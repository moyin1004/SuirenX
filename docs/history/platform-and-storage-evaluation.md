# 平台与存储候选评估

日期：2026-09-24。结论：这些候选项目前都不进入交付范围；当触发条件出现时，按本文定义开展小规模验证，再决定是否立项。

## 评估依据

- 当前产品规划假设近期以个人 Android 使用为主，尚无证明需要多平台、Web 管理或更高容量数据库的使用证据。
- Android 客户端使用 Room 作为资产与用品的唯一事实来源；服务端提供健康、认证和增量同步，不提供业务 CRUD。
- `api/proto` 是跨语言 HTTP JSON 契约；服务端仍是 Go/Hertz 模块化单体，仓储边界与 SQLite/GORM 实现在基础设施层。
- 资产持有天数和日均成本是常数时间的日期/整数运算；现有 Kotlin 领域实现和 Go 服务实现均有测试。本仓库没有该计算的性能基准或瓶颈报告。

## 决策

| 候选项 | 当前决定 | 进入验证的触发条件 | 首个验证边界 |
| --- | --- | --- | --- |
| 原生 iOS | 暂缓。保留原生客户端方向，不复用 Android UI 或移动 DTO。 | 有明确的 iOS 使用者/分发需求，并能安排维护者持续承担平台、签名和发布。 | 先以现有 HTTP JSON/Proto 合同做 Swift 兼容性 spike；再验证 iOS 本地持久化、事务式变更日志、幂等重试、冲突和备份恢复。暂不构建完整产品界面。 |
| Web 管理界面 | 暂缓。现有服务端没有资产/用品 CRUD，Web 页面不能直接管理业务记录。 | 出现可确认的桌面管理任务或多人运营场景，并先确定权限、服务部署和审计需求。 | 单独审查是否新增 Web 专用服务/API、认证、授权、CORS 与审计；保持移动端公开契约和本地优先规则不变，未经 ADR 不增加业务 CRUD 到现有移动同步 API。 |
| SQLite → PostgreSQL | 不迁移，也不现在演练真实用户数据库。SQLite 当前满足单机部署模型，且未提供容量、并发或可用性瓶颈证据。 | 选定的目标部署需要集中式高并发、多实例写入、托管备份/故障转移，或压测/运行数据证明 SQLite 无法满足服务目标。 | 先用合成数据复制现有 schema 和迁移约束；梳理 SQLite 专用 PRAGMA、立即写事务、partial/index 与查询差异；在仓储接口之下增加目标 dialect，运行相同服务/并发/冲突/幂等测试，记录耗时、差异、回滚步骤。未经独立决策不迁移任何用户数据。 |
| C++ 计算模块 | 不抽取。当前计算是常数时间整数和日期处理，没有实测热点；跨 Android/Go 的 C++ 绑定会增加 ABI、构建与调试成本。 | 先有可复现的 profile 指明稳定、占比显著的 CPU 热点，且纯 Go/Kotlin 优化无法满足已定义的性能目标。 | 固定真实代表性输入和性能基线，测量端到端收益及绑定开销；只对纯计算、输入输出明确的稳定接口做小型 spike，包含错误、日期边界、数值范围和跨平台构建。未达到预设收益即不采用。 |

## 共用约束

- `api/proto` 继续作为公开语言无关合同；不将 GORM 记录、Android DTO 或平台实体跨边界传递。
- Room 继续作为 Android 数据源；服务器部署或存储实验不能改变本地写入与同步 journal 的原子性。
- 数据库切换先在隔离环境用合成数据演练；若未来触及实际数据库，必须先备份、验证恢复和回滚方案，并遵守迁移规则。
- 每个候选进入实施前另立 ADR，记录需求证据、负责人、可测验收指标、维护成本和失败退出路径。
