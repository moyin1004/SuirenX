# 数据库迁移

服务启动前自动执行明确编号的 SQL 迁移，不再从 Go 模型推测如何改表。
迁移文件通过 go:embed 打包进可执行文件，部署时无需额外拷贝 SQL 目录。

| 版本 | 文件 | 内容 |
| --- | --- | --- |
| 001 | `001_init.sql` | 基线：资产表（含归档时间与图标标识）、状态与归档索引 |

`schema_migrations` 保存版本、文件名、SQL 内容的 SHA-256 和 UTC 执行时间。
重复启动只执行未应用的版本，已执行文件的内容或名称不一致时拒绝启动。
版本号是从 1 开始的连续整数，位数不限（001、002……999、1000 均可），
加载器按数值排序而非文件名字典序；建议文件名保持零填充以便目录浏览。

开发初期的三次结构变更已压缩进 001 基线。早于该基线的数据库（无
`schema_migrations` 记录，或记录的是压缩前的 001–003）不会被自动收养：
启动会因表已存在或文件名/校验和不匹配而回滚并中止，不会静默改造。
开发库直接删除 `services/api/data/` 下的数据库文件重建即可（文件不入库）；
需要保留数据时，先用旧版程序备份导出，再导入新建的数据库。

## 新增迁移

1. 在 `services/api/internal/database/migrations` 添加下一个连续编号，例如 `002_add_notes.sql`。编号为连续整数，超过 999 后直接使用 `1000_...`，加载器按数值排序。
2. 写明确的 SQLite SQL，必要时同步修改 repository 的记录和映射。
3. 已应用文件禁止修改、改名或删除；后续修正也添加新的编号。
4. 测试新库、旧版本升级、已有数据和失败回滚，运行 `cd services/api && go test ./...`。

迁移器统一管理事务，SQL 文件中不要写 BEGIN/COMMIT/ROLLBACK、VACUUM 或连接级 PRAGMA。
一个启动中的所有待执行迁移作为一个事务提交；任何一步失败会回滚整个待执行批次，
包括数据库结构、数据变更和迁移记录，然后停止服务启动。
写锁最多等待 5 秒，迁移阶段有 30 秒超时；大数据量迁移需另行规划停机窗口和执行方式。

## 升级与检查

升级前停止所有会写入该 SQLite 文件的服务，使用 SQLite 备份接口制作一致快照，
并保留对应旧版可执行文件。下例在 `services/api` 目录执行，备份文件名须使用新的名称：

```shell
sqlite3 data/suirenx.db ".backup 'data/suirenx-before-upgrade.db'"
```

运行新版 API，等待启动成功后检查健康接口和迁移历史：

```shell
curl --fail http://127.0.0.1:8888/healthz
sqlite3 data/suirenx.db 'SELECT version,name,applied_at FROM schema_migrations ORDER BY version;'
```

数据库路径仍可通过 `SUIRENX_DATABASE_PATH` 配置。备份文件与运行数据库一样不得提交到 Git。

## 失败与恢复

SQL 执行失败时，查看启动错误中标明的迁移文件；本次待执行批次已回滚，可修复尚未成功
应用的迁移后重试。若某文件已在其他环境应用，保留该文件不可变，先查明环境差异。

历史校验失败时，不要直接改 checksum 或删除版本记录来绕过保护：找到正确的可执行文件
或原始迁移文件。数据库版本比程序更新时，使用匹配的新程序，避免直接降级运行。

不提供自动向下迁移。已成功升级后如果需要回退，停止全部访问该数据库的进程，用升级前
备份恢复到一个新的数据库路径，再让匹配的旧版程序通过 `SUIRENX_DATABASE_PATH` 指向它。
这样也不会混用现有数据库旁的 WAL/SHM 文件。备份恢复会丢弃备份之后的写入，因此升级前
安排维护窗口，并在恢复前保留故障数据库以便核对。
